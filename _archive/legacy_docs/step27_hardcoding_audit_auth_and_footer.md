# [Step 27] 하드코딩 점검 및 로그인 인증/푸터 날짜 수정

> **작성일**: 2026-07-04
> **기준**: 사용자가 "프로그램에서 하드코딩된 부분을 점검해달라"고 요청

---

## 1. 조사

Explore 에이전트로 백엔드(`backend/`)·프론트엔드(`frontend/src/`) 전체를 훑어 하드코딩/조작 데이터를 점검. 이미 이전 스텝들에서 조치된 항목(PROB_FULL*0.15 근사치, PD-LAG 차트, LEGACY_BENCHMARK 등)은 제외하고 신규 발견분만 정리:

| 심각도 | 항목 | 위치 |
|---|---|---|
| 🔴 | 로그인이 아무 입력이나 통과됨 (실제 인증 없음) | `frontend/src/pages/LoginPage.tsx` |
| 🔴 | 푸터의 "최근 모델 업데이트: 2024-02-15 03:00 KST"가 완전히 고정된 문자열 | `frontend/src/App.tsx:148` |
| 🟡 | "고위험" 확률 임계값(0.5)이 프론트/백엔드 두 곳에 중복 하드코딩 | `BorrowerDetail.tsx`, `monitoring.py` |
| ⚪ | 매크로 시뮬레이션 목업 모드 계수 | 이미 "🧪 목업 모드" 버튼으로 명시적 라벨링되어 있고 실 API 실패 시 자동 전환되지 않음 — 문제 아님으로 판단 |
| ⚪ | `base_ym`/`branch_code` 기본 파라미터값, PD 구간 하드코딩 | 정상적인 API 기본값 설계 — 문제 아님 |

사용자 확인: 로그인은 간단한 계정 검증 추가, 푸터 날짜는 제거.

## 2. 조치

### 로그인 인증 (`backend/routers/auth.py` 신규, `backend/main.py`, `frontend/src/pages/LoginPage.tsx`)
- 신규 엔드포인트 `POST /api/auth/login`: `.env`의 `PORTAL_EMP_ID`/`PORTAL_PASSWORD`(기본값 `admin`/`admin1234`)와 대조, 불일치 시 401.
- `LoginPage.tsx`: 기존 "아무 값이나 넣으면 0.8초 후 통과"하던 로직을 실제 API 호출로 교체, 실패 시 에러 메시지 표시. 화면에 테스트 계정 힌트 노출.
- `mockup.html`: 백엔드가 없는 정적 파일이라 동일한 계정(`admin`/`admin1234`)을 클라이언트 측에서 검증하도록 반영(실제 앱과 동일한 로그인 경험 유지).

### 푸터 날짜 제거 (`frontend/src/App.tsx`)
- "최근 모델 업데이트: 2024-02-15 03:00 KST" 삭제 — 실제로 추적되는 값이 아니라 거짓 정밀도를 주는 문구였음. (`mockup.html`은 애초에 다른 안내문이라 해당 없음.)

## 3. 검증

- 백엔드: 틀린 계정 → 401, 올바른 계정(`admin`/`admin1234`) → `{"success": true}` 직접 호출로 확인.
- Playwright: 실제 화면·`mockup.html` 양쪽에서 틀린 계정 입력 시 에러 메시지 노출, 올바른 계정으로 정상 진입 확인. `npx tsc --noEmit` 통과, 콘솔 에러 0건(401 자체는 의도된 실패 시나리오의 정상 로그).

## 4. 남은 후속 과제 (미조치)

- "고위험 임계값 0.5"가 프론트/백엔드에 중복 하드코딩된 건 이번엔 손대지 않음 — 단일 소스화하려면 백엔드가 정책값을 API로 내려주는 구조가 필요해 별도 논의 필요.
- 지금 추가한 로그인은 고정 계정 1개만 지원하는 최소 구현 — 여러 사용자 계정, 세션/토큰 관리, 다른 API 엔드포인트 보호는 범위 밖(요청 시 별도 진행).
