# [Step 17] 차주 상세 데이터 정합성 및 중복 행 제거 작업 보고서

> **작성일**: 2026-07-02
> **기준**: Step 16 실모형 연동 이후, 실사용 중 발견된 리스트-상세 화면 간 등급/확률 불일치 버그 수정

---

## 1. 배경

Step 16에서 백엔드를 실제 DB/모델에 연동한 뒤 사용자가 직접 화면을 확인하는 과정에서, 지점 대시보드 리스트에서 특정 차주를 클릭했을 때 상세 화면의 등급·확률이 리스트와 전혀 다르게 나오는 문제를 발견함.

## 2. 발견 및 수정한 이슈

### 2.1 차주 상세 API가 기준월을 무시함
`GET /api/borrowers/{bzno}`가 `base_ym` 파라미터 없이 `SELECT * WHERE V_BZNO = ?`만 실행하여, 해당 차주의 66개월치 레코드 중 임의의(사실상 가장 이른) 행을 반환하고 있었음. 리스트는 특정 기준월(예: 2024-02) 데이터를 보여주는데 상세는 2021-01 데이터를 보여주는 식으로 완전히 어긋남.

- **조치**: `base_ym` 쿼리 파라미터를 받아 정확히 그 달의 레코드를 조회하도록 수정, 미지정 시 최신월로 폴백. `BranchDashboard.tsx`에서 상세 페이지로 이동할 때 현재 보고 있는 기준월을 URL(`?base_ym=`)에 포함하도록 수정.

### 2.2 프론트엔드 자체 등급 재계산 (3중 하드코딩)
`BorrowerDetail.tsx`와 `BranchDashboard.tsx`가 각각 별도의 하드코딩 함수로 등급을 재계산하고 있었음:
- 레거시 등급: `Z_GRADE`(G1~G5) 값 하나에 고정 문자열 5개를 매핑 (`"16등급 (C)"` 등) — 같은 Z_GRADE 안에서도 실제 부도확률이 37%~99%까지 다른데 전부 동일한 라벨 표시.
- ERM 등급: DB의 실제 `Z_GRADE`(Z-score 컷오프 -1/0/1/2 기준) 대신, 화면에서 `PROB_FULL`을 0.02/0.1/0.3/0.6로 나눠 재계산 — 두 기준의 확률 경계가 크게 달라(G4→G5 경계: DB 37.3% vs 화면 60%), VB001 지점 2024-02 데이터 기준 **73.8%의 차주에서 화면 등급이 실제보다 더 안전하게** 표시되고 있었음.

- **조치**:
  - 레거시 등급 배지·필터·검색을 삭제하고, 이미 실측 분위수 기반으로 계산되는 `NICE_GRADE_CUR`/`KIS_GRADE_CUR`(Step 16에서 추가한 `grade_mapping.py`)로 통일.
  - ERM 등급은 UI(배지 모양/색상)는 그대로 두되, 값 소스를 `PROB_FULL` 재계산에서 DB의 실제 `Z_GRADE`로 교체.

### 2.3 `corporate_panel`의 (V_BZNO, BASE_YM) 행 중복
동일 차주·동일 기준월 조합에 최대 289개 행이 중복되어 있는 사례를 발견 (예: 특정 차주 1개월치 289행 중 실제 값 조합은 5종류). 전체적으로 최신월 기준 약 6.5%, 전체 테이블 기준 약 12.5%의 행이 부풀려져 있었음. 원인은 `eda_pipeline`의 데이터 결합(join) 단계에서 발생한 것으로 추정되는 row fan-out (원본 CSV/파이프라인 재실행 없이는 근본 수정 불가 — 조사만 하고 쿼리 레벨에서 우회).

**영향받은 화면/지표**: 모니터링 차주 드릴다운(동일 차주 중복 노출, React key 중복 경고), 글로벌 뷰의 "전체 평가 기업 수"(부풀려진 값), PD 분포 비율, PSI 드리프트, 매크로 시뮬레이션 기준 모집단.

- **조치**: `backend/database.py`에 `dedup_panel_sql()` 헬퍼 추가 — `ROW_NUMBER() OVER (PARTITION BY V_BZNO, BASE_YM ORDER BY PROB_FULL DESC)`로 중복 중 부도확률이 가장 높은 한 행만 남기는 서브쿼리를 생성. `dashboard.py`, `borrowers.py`(상세 조회), `monitoring.py`(pd_distribution/drift/borrowers), `model_inference.py`(시뮬레이션 기준 모집단) 전체에 적용.

## 3. 검증

- 전체 평가 기업 수: 27,875(원본 행 수) → **26,184(중복 제거 후 실제 회사 수)**로 정정
- 모니터링 차주 드릴다운 20건 조회 시 중복 없이 **20개 전부 서로 다른 차주**
- 리스트(93.14%, G5, BB0) ↔ 상세(93.14%, G5, BB0) 완전 일치 확인
- Playwright로 글로벌/지점/모니터링/시뮬레이션 페이지 재점검, 콘솔 에러·경고 0건 (기존 React key 중복 경고도 함께 해소됨)

## 4. 후속 과제

- (V_BZNO, BASE_YM) 행 중복의 근본 원인은 `eda_pipeline` 데이터 결합 단계에 있음 — 원본 CSV를 다시 확보해 파이프라인을 재실행하지 않는 한 쿼리 레벨 우회(dedup)로만 대응 가능.
