## 1. 데이터의 구조적 한계

가공이나 모델링으로 고칠 수 없고, **데이터 자체의 성질**에서 오는 한계다. 각 항목은
관련 문서로 연결한다.

### 1-1. 가상 사업자번호

패널의 `V_BZNO` 는 실제 사업자번호가 아니라 대회용으로 생성된 가상 식별자다. 기업
단위 집계(부도 기업 988사, 상위 X% 포착률 등)는 이 식별자에 의존하므로 **실데이터에서
같은 절차를 돌렸을 때 값이 그대로 재현된다는 보장이 없다.** 절대 수치보다 구조와
방향(포착률의 단조성, 레버리지 비례 반응)을 근거로 읽어야 한다. (06 문서 §6-2)

### 1-2. 예측 대상이 "당행 손실" 이 아니다

부도 이벤트 1,286건 중 **부도사유 41(타행불량)이 1,143건 = 88.9%** 다 (원천
`도메인값.txt`·BUDO 집계, `logs/C2_docs_01_02_03.log`). 즉 이 모델이 예측하는 것은
"당행 차주가 **어딘가에서** 부실화되는 사건" 이고, 당행 자체 대손과는 다르다.
경보가 곧 당행 손실 예측은 아니라는 점을 06 문서의 임계값·비용 논의와 함께 읽어야
한다. (01 문서 타겟 정의)

### 1-3. 관측 기간에 금리 사이클이 한 번뿐이다

거시 지표는 `BASE_YM` 하나당 값이 하나이므로 모델이 거시로부터 배울 수 있는 실질
표본은 행수(948,214)가 아니라 **월 수(53)** 다. 그 53개월에 금리 인상→고점→인하가
**한 번** 들어 있어, 금리·스프레드 계열의 부호가 그 한 사이클에 묶인다 — 차분·수준·
누적 어느 형태로도 Train↔Valid 에서 부호가 뒤집힌다. 거시 상호작용의 방향을
주장하려면 최소 2개 사이클을 덮는 기간이 필요하다. (05 문서 §5 · §7, 06 문서 §4)

### 1-4. 내부 조기경보모형 부도율이 11개월만 있다

`OBV_RZVL_POD` 가 202101~202111 (전부 저금리기·전부 Train)에만 값이 있고 이후 전 행
0 이라, 내부 모형과의 어떤 비교도 조건이 성립하지 않는다. 상세와 조치는 §4-12.

### 1-4-1. VH_OBV_DTL 금액 컬럼 5개 — 초기 D8 에 들어가 있던 죽은 피처 (제거 완료, 이력으로 남김)

`OBV_RZVL_POD` 와 **동일한 창**(202101~202111, 11개월)만 값이 있고 202112 이후 전 행
0 인 컬럼이 5개 더 있었다. **초기 D8(169피처)에는 이 5개가 피처로 포함돼 있었다.**

| 컬럼 | 뜻 | 비영률 ~202111 | 비영률 Valid(202401~) | 초기 D8 gain | Lean(포털) |
|---|---|--:|--:|--:|:--:|
| `OBV_XPC_LSS_AM` | 예상손실금액 | 99.85% | **0.00%** | 1.900% | 포함했었음 |
| `OBV_BZL_RZVL_ASP_ELGD` | 바젤 추정 ELGD | 99.78% | **0.00%** | 0.902% | 포함했었음 |
| `OBV_LN_BAC` | 여신 잔액 | 89.94% | **0.00%** | 0.607% | 포함했었음 |
| `OBV_LN_LMT_BAC` | 대출한도잔액 | 16.99% | **0.00%** | 0.399% | — |
| `OBV_LN_LMT_AM` | 대출한도금액 | 17.16% | **0.00%** | 0.049% | — |
| **합계** | | | | **≈ 3.86%** | |

- Dev·Valid 전 구간에서 값이 0 이므로 **해당 구간 예측에서는 "= 0" 한쪽 분기로만
  작동** — 사실상 죽은 피처다. `OBV_RZVL_POD` 는 애초에 피처에서 제외했으나
  이 5개는 걸러지지 않았다. gain 3.86% 는 Train 에서 학습된 split 의 기여이지 Valid
  기여가 아니다 (04 문서 §7-3 5번의 교훈).
- **조치: 5개를 제외하고 재학습했다.** Valid AUC 가 **0.8548 → 0.8578** 로 0.003
  오르고 시드 σ 도 **0.0015 → 0.0007** 로 절반이 됐다. 현행 D8 은 164피처이고
  포털 서빙 `lgbm_v2_lean_macro.txt` 도 59피처로 재산출했다. 등급 컷오프·μ/σ·
  임계값·포털 DB(`portal_v2.duckdb`)를 전면 재산출했다(2026-09-04). 구세대 산출물은
  `_archive/superseded_d8_169/` 에 보존한다. 경위: 04 문서 §7-3 (5번).
- **정상인 것**: `OBV_LD_AM`(부도시손실금액, SHAP 상위 1위) 은 Valid 비영률 99.38%
  로 전 구간 채워져 있어 제외하지 않았다. `OBV_ELYWRN_OBV_GRD_DSC`(조기경보관찰등급)
  도 Valid 전 구간 A/B 값이 있다. 같은 원천이지만 이 둘은 문제없다.
- **포털 영향**: 재학습 전 `/api/borrowers/{bzno}/shap` 실측(차주 8명, PD 3.3~93.5%)
  에서도 이 3개는 SHAP 절댓값 상위 8개에 **나타나지 않았다**(값 0 → 기여 ≈ 0). 교체
  후에는 서빙 모델에서 아예 빠졌다.

### 1-5. `CG01` 은 월 단위로 되살릴 수 없다

원천이 연도별 wide 포맷(`KIS_LS_FNA_MKS_2021~_2025`)이고 날짜 컬럼이 없다. as-of
재구성이 원천적으로 불가능해 `LEAK_CONFIRMED` 로 확정 제거했다. (04 문서 §3-1)

### 1-6. AC12 외화부채가 연 단위 조인분이다

`AC12_*` 계열과 그 파생(`exp_fx_dbt`, `fx_vol_x_fxdebt`)은 상류가 연 단위 조인이라
시점 부분오염((d))을 포함한다. 월 단위 as-of 로 해소됨을 확인했으나(기여 +0.00067,
노이즈) 본류 반영 시 전 축 기준선이 함께 이동해 이번 범위에서 적용하지 않았다.
상세는 §2-1.

## 2. 알고도 남겨 둔 결함

### 2-1. AC12 시점 부분오염 — 해소 경로는 확인했으나 적용하지 않았다

`exp_fx_dbt` 및 `fx_vol_x_fxdebt` 는 상류 `AC12_TOTAL_KRW_AM` 이 연 단위 조인분이라
시점 부분오염((d))을 포함한다. AC12 를 월 단위 as-of 로 재조인하면 해소됨을
확인했으나(B46 — step31 재판정에서 (b) 11개·(d) 2개가 모두 해소, 성능 기여는
A0 대비 **+0.00067** 로 노이즈), 본류(`step2`/`step5`) 반영 시 A/B/C/D **전 축의
기준선이 함께 이동**하므로 이번 범위에서는 적용하지 않았다.

영향 크기는 제한적이다 — 해당 변수들은 전 시나리오에서 **gain 상위 20 밖**이며
`fx_vol_x_fxdebt` 는 D3 에서 gain **0.000~0.023%(89~177위)** 다.

- 범위: `AC12_*` 금액 10개 + `HAS_AC12_YN` 은 **(b) 시점누수**, `exp_fx_dbt` 는
  **(d) 부분오염**. 이 컬럼들은 A0 피처 풀에 있어 **D0 를 포함한 전 시나리오가
  공유**한다. 시나리오 간 ΔAUC 비교는 공정하지만 **절대값은 이 오염을 포함**한다.
- `HAS_AC12_YN` 이 피처에 살아 있어 모델은 "금액 0 = 외화부채 없음" 과
  "레코드 없음" 을 구분할 수 있다. 추가 플래그는 필요하지 않다.
- 추적: `PENDING_REVALIDATION.md` 12번.

> ★ **미완(열린 항목):** AC12 월 단위 as-of 본류 반영은 전 축 기준선 이동을 유발해
> 적용하지 않았다. `fx_vol_x_fxdebt` 에 (d) 부분오염이 잔존한다.

### 2-2. `CG01` 계열 — 월 단위 재구성이 원천적으로 불가능하다

원천이 연도별 wide 포맷(`KIS_LS_FNA_MKS_2021~_2025`)이고 날짜 컬럼이 없다.
`LEAK_CONFIRMED` 로 확정 제거했고, 되살릴 방법이 없다.

### 2-3. `CRIF` 계열 — 정합화해도 기여가 노이즈여서 되살리지 않았다

월 단위 as-of 로 재구성해 기여를 실측했으나 노이즈 범위였다.
정합화 자체는 가능하나 실익이 없어 제거를 유지한다. 근거는 04 문서에 있다.

## 3. 측정 방법에 남은 의존성

### 3-1. 거시 공표 시차의 근거는 **하루치 관측**이다

시차 근거는 **2026-09-01(월초) 관측**이며, 월초 측정은 직전월 공표를 반영하지
못한다. **재수집 시 월말 관측으로 재검증할 것.**

- 가드(`data_collector.check_publication_lag`)는 측정일이 그 달 15일 이전이면
  경과에서 1개월을 뺀다. 단 **월간 공표 계열에만** 적용한다 — 분기 계열에는
  놓칠 직전월분이 없으므로 보정하면 실제 지연을 깎아 버린다.
  관측 주기는 설정값이 아니라 받은 데이터에서 실측한다.

> ★ **미완(열린 항목):** 경계선 15건의 시차 재판정은 월 중순 이후 공표 관측이 필요해
> 미완이다. 해당 컬럼은 대부분 물가·통화 지표이며 D8 gain 상위 20 에 없다.
- 이 보정을 도입한 근거: 임계를 `lag > shift` 로 조였을 때 걸린 15건의
  `경과 − 시차` 가 **일률적으로 +1** 이었다. 시차가 다른 두 그룹(B·C)에서 편차가
  같다는 것은 지표 특성이 아니라 **측정 방법의 공통 편향**을 가리킨다.
- 상세: `api_data_processing/data_preprocessing.md`,
  `docs/appendix/audit/PUBLICATION_LAG_AUDIT.md`.

### 3-2. 관측 기간에 금리 사이클이 한 번뿐이다

거시 지표는 `BASE_YM` 하나당 값이 하나이므로 모델이 거시로부터 배울 수 있는
실질 표본은 행수가 아니라 **월 수**다. 그 기간에 사이클이 하나뿐이라
시차·부호에 관한 어떤 선택도 그 한 번에 과적합될 수 있다. 05 문서 참조.

## 4. 재현성 사고 사례

기록 목적은 재발 방지다. **실제로 발생한** 사고만 적는다.

### 4-1. 결과 파일 전체가 덮어써져 14개 시나리오가 지워졌다

`step30_stage6_ablation` 의 초판은 부분 실행 시 결과 JSON **전체를 교체**했다.
`--run C4 C5` 를 돌린 순간 앞서 돌린 **14종이 지워졌다.** `step30._merge_results`
docstring 이 그 사고를 기록하고 있다 —
*"예전 구현은 파일 전체를 [C4, C5] 로 교체해 앞서 돌린 14종을 지워 버렸다
(실제로 한 번 발생했다)."*

병합 로직은 **사고 이후** 추가됐고, 그때 데이터는 이미 사라진 상태였다.
결과적으로 A축 확정판의 원자료 JSON 이 유실되어 **리포트 표가 유일한 기록**으로
남았다. 같은 형태가 `seed_variance_probe.json` 에도 있었고(실행마다 덮어쓰기)
2026-09-02 에 병합으로 교체했다.

**교훈**: 측정 결과 파일은 **append/merge 를 기본값**으로 둔다. 부분 실행이
전체를 교체할 수 있는 구조는 그 자체로 결함이다.

### 4-2. 시나리오 정의가 바뀌어 저장값의 의미가 반대가 됐다

`C302` 정합분이 A0 에 편입되면서 `A5`·`A6` 가 **"추가" 시나리오에서 "제거"
시나리오로 전환**됐다. 구세대 JSON 의 A5·A6 값을 현재 코드의 시나리오 설명으로
읽으면 **정반대 해석**이 된다.

- 각 레코드에 `desc` 가 남아 있어 판별은 가능하다. **반드시 함께 읽을 것.**
- 자동 검출: `python -m eda_pipeline.audit_feature_counts` —
  피처 수를 시나리오 명세와 대조하고, `desc` 가 바뀐 기록을 **"정의 변경분"으로
  분리 출력**한다 (조인 누락과 구분하기 위해서다).

### 4-3. 측정하려던 피처가 조인되지 않은 채 라벨만 붙어 돌았다

`--seed-probe A2` 가 되넣기 컬럼(CRIF 4개)을 조인하지 않아, "A0 + 누수 4개" 를
재려던 시나리오가 **A0 와 동일한 피처 152개**로 돌면서 라벨만 A2 였다.
AUC 가 A0 와 시드까지 완전히 같게 나온 것으로 발견했다.

이 값을 믿었다면 **"CRIF 누수 기여가 없다"** 는 정반대 결론이 나올 수 있었다.

**조치**: `resolve_features` 에 `strict=True` 를 넣어 되넣기 컬럼이 패널에 없으면
**예외로 중단**한다. 측정하려던 것을 측정하지 못했으면 결과가 아니라 오류다.

### 4-4. 시드 3회로 관찰한 안정성 차이가 10회에서 축소됐다

`fx_shock_x_export`(gain 0.000, 최하위)를 **빼면** 캘리브레이션 시드 분산이
커지는 현상을 관찰했다. 시드 3회에서는 그 차이가 **약 10배**로 보였다.

시드를 10회로 늘려 다시 재니 **1.5~1.8배**였다.

| | 시드 3회 관찰 | **시드 10회 실측** |
|---|---|---|
| 상관 σ (D7m → D6m) | 0.1246 → 0.0347 (**3.6배**) | 0.0741 → 0.0410 (**1.8배**) |
| MAPE σ (D7m → D6m) | 5.96 → 0.62 (**9.6배**) | 4.85 → 3.20 (**1.5배**) |
| D6m 보정 평균PD 범위 | 0.41~0.42% (안정으로 보였다) | **0.39~0.52%** |

> **교훈**: 시드 3회는 σ 자체를 **과소추정**한다. D6m 의 MAPE σ 는 3회에서 0.62,
> 10회에서 3.20 으로 **5배** 커졌다. 안정성을 근거로 구성을 결정할 때는
> 충분한 반복이 필요하다. 이것은 다른 프로젝트에도 그대로 적용되는 교훈이다.

또한 이 정정으로 **D7m(2종) 채택 근거가 더 약해졌다.** gain 0.000 인 변수를 넣어
얻는 것이 10배가 아니라 1.5~1.8배라면, "예측에 기여하지 않는 변수를 안정성 목적으로
넣었다" 는 설명이 심사에서 더 어려워진다. D6m 확정이 옳았음을 뒷받침한다.

### 4-5. gain 0 인 피처 추가가 시드 분산을 줄이는 현상 — 원인 미규명

`fx_shock_x_export` 는 gain **0.000**, 순위 최하위로 **한 번도 분기에 쓰이지
않았다.** 그런데 이 변수를 넣은 구성(D6m)이 뺀 구성(D7m)보다 캘리브레이션 시드
분산이 작다 (상관 σ 0.0410 vs 0.0741, MAPE σ 3.20 vs 4.85).

**피처 샘플링 경로 변화로 추정된다** — 피처가 하나 늘면 `feature_fraction` 이
고르는 조합이 달라진다. 성능(gain·AUC)이 아니라 **안정성에만** 영향을 준다.
**원인은 규명하지 못했다.**

### 4-6. 리포트 생성기가 서술에 수치를 하드코딩하고 있었다

재실행하면 표는 갱신되는데 **서술이 옛 수치를 계속 주장**하는 구조였다.
`step30~35` 범위에서 하드코딩 기대값·분할 경계 **6곳**을 발견해 데이터 파생으로
교체했다. 특히 분할 경계를 `split_spec` 대신 상수로 박아 둔 곳이 있어, 분할을
바꾸면 모델은 새 분할로 학습하는데 진단만 옛 경계로 계산되고 리포트가 둘을 같은
분할로 제시할 수 있었다. **현재 값이 우연히 일치해 수치는 바뀌지 않았고, 잠재
위험만 제거했다.**

또 산출물에만 정정 주석을 달고 생성기를 고치지 않으면 **재생성 때 무효 서술이
되살아난다**. 실제로 2026-09-01 에 무효 판정된 논거가 생성기에 남아 있었다.

### 4-7. backend 가 이 저장소에서 동작한 적이 없다 — 결함 3건은 전부 기존 문제였다

**동작을 검증하지 않은 코드는 동작하지 않는다.** 포털 backend 가 그 사례다.
아래 3건은 새로 만든 패널이나 새 화면 때문에 생긴 것이 아니라, **처음부터 있었고
아무도 실행해 보지 않아서 드러나지 않은** 결함이다.

**(1) DB 경로가 존재하지 않는 파일을 가리키고 있었다**

`backend/database.py:7-11` 의 주석이 그 상태를 기록하고 있다 —
*"초판은 `database/portal.duckdb` 를 하드코딩했는데 **이 체크아웃에는 그 파일이

이 저장소에서 backend 가 동작한 적이 없다)."*

`portal.duckdb` 가 없다는 것은 독립적으로도 확인된다 —

backend 라우터 3개가 이 두 컬럼에 의존한다 —

|---|---:|---|
| `database/portal.duckdb` (legacy) | — | **파일 자체가 없음** |

**(3) 사업자번호 비교 — 결함은 확인됐으나 원인은 "선행 0 손실" 이 아니었다**

지시받은 가설은 `V_BZNO` 를 `int()` 로 변환해 비교하면서 **선행 0 이 손실**된다는
것이었다. 절반만 맞다. 정직하게 적는다.

- **`int()` 변환 비교는 실재했다.** `backend/routers/borrowers.py.bak:192`·`195` —
  `if df.empty or not (df['V_BZNO'] == int(bzno)).any():` / `target = df[df['V_BZNO'] == int(bzno)].iloc[0]`.
  이 파일은 2026-09-03 수정 이전의 라우터 사본이며, `.bak` 확장자라 현재는
  import 되지 않는다(`docs/appendix/A4_portal_status.md` §1 참조).
  현행 코드는 `backend/routers/borrowers.py:237-245` 에서 문자열 비교로 교체됐고,
  같은 자리에 `[2026-09-03]` 주석으로 사유가 남아 있다 —
  *"`V_BZNO` 는 새 패널에서 **VARCHAR** 다. int 로 캐스팅해 비교하면"* 성립하지 않는다는 것이다.
- **선행 0 손실은 이 데이터에서는 발생하지 않았다.** `corporate_panel` 의 `V_BZNO`
  는 현행·백업 DB 모두 `VARCHAR` 이고, `'0'` 으로 시작하는 값이 **0건**이다
  (읽기 전용 실측). 따라서 실제 파손 원인은 자릿수 손실이 아니라 **VARCHAR ↔ int
  비교가 아예 성립하지 않는 것**이며, 결과는 모든 차주에 대해 조건이 항상 거짓이
  되어 **404 를 반환**하는 것이었다.
- **이 결함이 새 패널과 무관하게 원래부터 있던 것인가**는 저장소 안의 근거만으로는
  단정할 수 없다. `.bak` 이 그 코드가 라이브였음을 증명하지만, 구 스키마에서
  `V_BZNO` 가 정수형이었다면 그때는 동작했을 수 있다. 확인 가능한 두 DB(현행·백업)
  에서는 둘 다 `VARCHAR` 다. **"확인된 것은 결함의 존재이고, 도입 시점은 미확인"**
  으로 남긴다.

세 건을 합치면 결론은 하나다. **README 기재 포털 기능 중 일부는 동작이 검증된 적이
없다.** 실제로 2026-09-02 야간 실행에서도 검증은 완료되지 못했다 —
`fastapi`·`uvicorn` 이 두 인터프리터 모두에 없어 기동 자체가 중단됐고

산출물이 로컬에만 있었고 커밋에서 빠진 것이다(`portal.duckdb` 와 같은 경우다).

**"별도 보관본에서 복원했다" 는 근거는 찾지 못했다.** 오히려 반대 기록이 있다 —
같은 문서는 *"상위 폴더(`sy/NH AI경진대회/`) 전체를 탐색했으나 거시 CSV 는 발견되지
않았다"* 고 적고 있고, 조치 7번의 상태는 **"신규 작성"** 이다
(`api_data_processing/collect_macro.py`, 2026-08-30). 즉 복원이 아니라 **재작성**이며,
복원 근거는 모델 파일에 남은 피처명을 역파싱한 명세
(`eda_pipeline/output/macro_respec_from_model.json` — 거시 172개 = 원지표 63개 ×
변환 2~4종)뿐이다. `collect_macro.py:1-12` 의 모듈 docstring 이 같은 사실을 다시
적고 있다.

남은 결함도 그대로 기록한다. 원본 CSV 는 **미확보**이며 재수집으로 대체한다
(PENDING 8번). STAGE 5 는 이 파일 없이 `default_rng(20260829)` **합성 프레임**으로
로직만 검증했고, **그 합성값이 `portal_v2.duckdb` 에 들어가 있다 — 학습에 쓰면
안 된다** (`collect_macro.py:14-17`).

### 4-10. 이미 기록된 사고들 — 중복 서술하지 않는다

- **A축 원자료 JSON 유실**: `4-1` 참조. 부분 실행이 결과 파일 전체를 교체해 14개
  시나리오가 지워졌고, 리포트 표가 유일한 기록으로 남았다.
- **하드코딩 기대값·분할 경계 6곳**: `4-6` 및 `5절` 참조. 데이터 파생으로 교체했다.
- **`step8`~`step27` 이전 세대 생성기 미점검**: `5절` 참조. 동일 패턴이 남아 있을
  가능성이 있으며 이번 범위에서 점검하지 않았다.

### 4-11. 하나의 주제 — 동작을 검증하지 않은 코드는 동작하지 않는다

`4-1`(부분 실행이 결과 JSON 전체를 덮어씀), `4-6`·`5절`(생성기가 서술에 수치와 분할
경계를 하드코딩), `5절`(`step8`~`step27` 이전 세대 생성기 미점검), 그리고 거시 수집
스크립트가 레포에 아예 없었던 일(`4-9`)까지, 이 문서의 사고들은 형태가 달라도 원인이
같다. **한 번도 실행해 확인하지 않은 경로는 예외 없이 깨져 있었다.** `4-7` 은 그
전형이다 — 없는 파일을 가리키고, 없는 컬럼을 조회하고, 타입이 맞지 않는 비교를 하는
코드가 나란히 살아 있었다.

`4-8` 은 방향이 반대인데도 같은 원인에서 나온다. **동작을 확인하지 않고 화면만 지우면,
그 아래에는 아무도 부르지 않는 계산이 남는다.** 미검증 코드가 죽어 있는 것과, 검증
없이 지운 화면 아래 계산이 사문화되는 것은 같은 습관의 앞뒷면이다. 재발 방지는
"검증했다" 를 근거와 함께 남기는 것뿐이다 — 기동 로그든, 응답 스냅샷이든,
읽기 전용 실측 표든.

### 4-12. 내부 조기경보모형과의 직접 대조를 하지 못했다

벤 다이어그램 분석(C-1)은 **내부 조기경보모형(EWS)의 부도율 `OBV_RZVL_POD` 와 우리
모형(D8)의 예측 PD 를 상위 X% 로 교차**해, 두 모형이 각각 잡는 부도 기업이 얼마나
겹치는지 보려 했다. **원천 데이터의 한계로 수행하지 못했다.**

- `OBV_RZVL_POD` 는 원천 `가상사업자_VH_OBV_DTL_관찰세부등급v.txt` 에서 **202101~202111
  (11개월) 에만 값이 있고, 202112 이후 전 행이 0** 이다 (raw 970,459행 실측).
- 값이 있는 11개월은 **전부 학습 구간(TRAIN)** 이고 **전부 저금리기**다. 국면(저금리 ↔
  긴축 ↔ 인하) 간 비교도, 홀드아웃 대조도 불가능하다. 이 창에서 낸 어떤 수치도
  in-sample · 단일 국면이라 해석할 수 없어 최종 산출물(`C1_venn_results.md`)에서
  **A 파트를 통째로 뺐다.**
- 준비 스크립트 `step39_venn_prep` 의 `budo_pod_coverage = 1.0` 은 **NULL 이 아니라
  값 0 을 "커버됨" 으로 집계한 오탐**이었다. "부도 기업 988사 전부 내부 모형 값 보유"
  로 읽혔으나, 실제로는 202112 이후 부도 기업의 `OBV_RZVL_POD` 가 전부 0(결측을 0 으로
  채운 값)이었다.

**영향**: "내부 모형 대비 리드타임", "내부 모형이 놓친 부도를 우리 모형이 잡았다"
류의 **직접 비교 주장은 이 저장소의 데이터로는 뒷받침되지 않는다.**

- in-sample·단일 국면 AUROC 를 산출해 각주로 다는 방식도 **채택하지 않았다** — 표에
  숫자 두 개가 나란히 있으면 각주와 무관하게 비교로 읽히기 때문이다.
- 이전 세대 산출물과 README 에 남아 있던 **'내부 모형 AUROC 0.77 대비'** 류의 주장
  (서로 다른 세 값 0.77 / 0.823 / 0.654 이 기록돼 있었다)은 근거를 확인할 수 없어
  **폐기한다.** README 의 벤 다이어그램·"내부 모형 대비" 서술도 전부 제거했다.
- 06 문서의 재무양호군 분석(§2)은 "내부 모형이 재무 기반" 이라는 사실에 기댄
  **간접 증거**로만 서술했다.

## 5. 점검하지 않은 범위

`step30~35` 범위에서 **하드코딩 기대값·분할 경계 6곳을 발견해 데이터 파생으로
교체했다.** `step8`~`step27` 의 이전 세대 생성기에 **동일 패턴이 남아 있을 가능성이
있으며, 이번 범위에서는 점검하지 않았다.**

발견·교체한 6곳
1. `step33` G1-7 프로브의 기대 시차 고정값 → `impute_data.GROUP_*_COLS` 파생
2. `step35` §0 `rate_shock_x_leverage` 의 충격 0 비율 `53.14%` → 게이트 1 기록에서 읽음
3. `step35` §3 같은 값이 **두 번째로** 하드코딩된 것 → 동일 조치
4. `step35` §4 `ACTUAL_YEARLY` 연도별 부도율 상수 → 패널 실측
5. `step35` §5 분할 경계 6개소(`"202310"`·`"202401"` 등) → `split_spec` 파생
6. `step34` `interaction_gain` 이 구 상호작용 집합만 보던 것 → D6/D7/E14 포함

> 6번은 D8 의 상호작용 14개가 전부 `gain 0.000` 으로 보이게 만들었다. 거시 gain
> 0.93% 와 모순되는 것을 보고 잡았다. **집합에 새 항을 추가할 때마다 갱신하지 않으면
> 같은 일이 반복된다.**
